# autopoesis-core

A minimal, file-driven core for deterministic state evolution.

## Operating model

1. Put tasks in `TASKS.json`.
2. Run `python run_tasks.py`.
3. Read task outcomes from `RESULTS.json`.

The core has no user accounts, internal authorization framework, network service, external dependencies, or required API credentials.

## Current capabilities

- Deterministic JSON state digest using SHA-256 for content identity.
- A small evolution operation that accepts a meaningful state change and rejects a no-op.
- Explicit, bounded task types rather than arbitrary shell or Python execution from task data.
- Machine-readable results written to a file.
- Static discovery of TODO/FIXME/HACK markers and source modules without conventional tests.
- A JSON task queue with stable candidate IDs, duplicate suppression, lifecycle statuses, attempt counts, status history, and persisted verification-evidence records.
- Queue updates are written to a same-directory temporary file and atomically replace the prior snapshot, so an interrupted write does not expose a partially serialized queue.
- A replaceable `CodeWriter` interface and a bounded built-in writer that prepares a deterministic import-test patch artifact for an eligible Python module.
- Standard-library-only tests and CI.

## CI and result files

Every push to `main` and every pull request runs the tests and task runner on Python 3.12. The workflow uploads generated `RESULTS.json` and `TASK_QUEUE.json` as the `autopoesis-core-results` artifact.

To inspect a run, open [GitHub Actions](https://github.com/Autopoiesis-Intelligence/autopoesis-core/actions), select the run, and download the artifact from its **Artifacts** section. Generated execution files are artifacts, not committed source files; this keeps runtime output separate from source history. When running locally, `TASK_QUEUE.json` remains on disk between runs. Each GitHub Actions run starts from a clean checkout. To restore a prior snapshot in CI, manually start the **CI** workflow with `restore_run_id` set to the numeric ID of a prior successful run from this repository's `.github/workflows/ci.yml` workflow. Before downloading its artifact, the workflow verifies that the source run concluded successfully and belongs to the expected repository/workflow. It requires exactly one unexpired `autopoesis-core-results` artifact bound to that run and records the artifact ID, archive digest, size, and creation time in `QUEUE_RESTORE_PROVENANCE.json`. Each uploaded artifact also contains `QUEUE_SNAPSHOT_MANIFEST.json`, which binds the queue file's SHA-256 and size to the producing run ID, repository, and commit SHA. During restore, the workflow checks the manifest's run ID and commit SHA against the verified source run, recomputes the queue file SHA-256, validates it using the queue loader, and only then installs it for the task runner. The restore provenance records the source manifest hash and the restored queue hash. These checks establish run binding and internal consistency, not a cryptographic signature: the queue and its manifest are members of the same artifact, so a party able to replace both can recompute the manifest. The artifact archive digest is recorded from GitHub metadata but is not independently recomputed by this workflow. If the source run was unsuccessful, the artifact or queue file is missing, or the queue is invalid, the restore run fails instead of silently starting with an empty queue. Runs without `restore_run_id` retain the existing clean-checkout behavior. For an explicit two-run persistence check, start the first run with `seed_done_probe=true`; then start a second run with that first run's numeric ID as `restore_run_id`. Any restore run now requires both the synthetic `DONE` status/history and a synthetic verification-evidence record, and fails if either is absent. Ordinary CI runs skip these cross-run probes.

## Important boundary

This starter can execute the task types implemented in `run_tasks.py`. A task description alone cannot cause the program to invent and write new code. The `prepare_test_patch` task generates a reviewable patch artifact for one narrow case: adding an import-smoke test for an existing module under `autopoesis/`. It does not modify source files, apply patches, or run generated code. `apply_test_patch_sandbox` writes a validated patch only into an explicit disposable sandbox and does not execute it. `verify_test_patch_sandbox` copies the package into a temporary workspace and executes only the generated import-smoke test with a bounded timeout; importing the package can execute its top-level Python code, so this is a bounded temporary workspace, not a hardened security sandbox. The task reports verification evidence separately and does not automatically mark the queued task `DONE`. Generated patches are not applied to repository source files automatically. A future external or local model can implement the same `CodeWriter` interface without changing the core task contract.

## Run

```bash
python run_tasks.py
python -m unittest discover -s tests -v
```

Edit `TASKS.json` to configure work. `queue_discovered_tasks` merges newly discovered candidates into `TASK_QUEUE.json` without duplicating existing IDs or overwriting their statuses. Use `update_task_status` with `task_id`, `status`, and optional `note` to persist a lifecycle change. The default `CORE-005` task invokes `prepare_test_patch` for `autopoesis/task_queue.py`; it places a reviewable generated patch in `RESULTS.json` on each run. Before returning the artifact, the writer validates artifact and file hashes, allowed output paths, duplicate paths, and Python syntax without executing generated code. `CORE-006` applies the same patch inside a disposable temporary sandbox and reports the result; the sandbox is removed after the task, and repository files are not modified. Additional `prepare_test_patch` tasks can target eligible modules by specifying an `id` and `source` path. Generated patches are not applied to the repository automatically. The separate `apply_test_patch_sandbox` task exercises file creation in a disposable directory and never executes generated code. Supported statuses are `OPEN`, `SELECTED`, `IN_PROGRESS`, `DONE`, and `REJECTED`; moving a task to `IN_PROGRESS` increments its attempt count. `update_task_status` enforces the lifecycle in `ALLOWED_TRANSITIONS`: `OPEN → SELECTED → IN_PROGRESS → DONE`, with `IN_PROGRESS`/`SELECTED → OPEN` for retries and `REJECTED` reachable from any non-terminal status. `DONE` and `REJECTED` are terminal, repeating the current status is a no-op, a task cannot enter `IN_PROGRESS` more than `MAX_ATTEMPTS` (3) times, and `DONE` requires that the latest verification recorded for that item since its last `IN_PROGRESS` is a `PASS` for the item's own `source` that names the same git `commit_sha` and `tree_sha` as the `DONE`. Only the coordinator (`python -m autopoesis.orchestrator`) sets `DONE`: it runs the handler on a `git archive` snapshot of the checkout's `HEAD` and records that commit and tree; `update_task_status` refuses `DONE`. Queue files from versions 1 and 2 must first be migrated with `python -m autopoesis.task_queue migrate`; their old `DONE` events keep their old meaning and are not upgraded. Verification evidence for a queued item must name that item's `source`, so a check of one file cannot be credited to a task about another, and an item without a `source` cannot reach `DONE`. A `verify_test_patch_sandbox` task records its evidence under `queue_task_id` when given, which links it to a queue item. The `select_next_task` task picks one `OPEN` item deterministically and moves it to `SELECTED`. It ranks by integer `priority` (higher first), then fewest attempts, then id. It reports why every other item was deferred: missing `source`/`evidence`, the attempt limit, or ranked lower. It selects nothing while another item is `SELECTED` or `IN_PROGRESS`, and with no eligible work it leaves the queue unchanged. The queue module has no unchecked status writer: every status change goes through `advance_task`/`advance_task_file`. Entering `SELECTED` grants a lease (`owner`, random `token`, `expires_at`, default 30 minutes) and only one item may be active at a time. Every later change of an active item, including recording its verification evidence, needs the current unexpired token, and `renew_lease` extends it for the holder only. `recover_expired_leases` (also a task type) returns items whose lease expired, or that have none, to `OPEN` with a `LEASE_EXPIRED` history event; an executor that resumes after expiry is refused with `STALE_LEASE`. A PASS counts toward `DONE` only if recorded under the item's current lease. The runner replaces `RESULTS.json` on each run so the file represents the latest run. Use `python run_tasks.py --queue path/to/TASK_QUEUE.json` to choose a queue file.
