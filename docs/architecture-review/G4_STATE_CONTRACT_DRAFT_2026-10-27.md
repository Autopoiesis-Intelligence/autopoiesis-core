# G4: контракт состояния ядра (черновик)

Claude, 2026-10-27. Статус: **черновик**, не согласован с GPT и не утверждён владельцем. Схема из решения владельца от 13:13 UTC: этап 1 — временное состояние без заявления об автономном продолжении; этап 2 — отдельная ветка операционного состояния. В черновик входит раздел G3 о гонке между проверкой и DONE.

## 0. Термины

| Термин | Значение |
|---|---|
| Авторитетное состояние | то, из чего следующий запуск обязан исходить и что нельзя заменить ничем другим |
| Временное состояние | живёт не дольше одного запуска; потеря не меняет авторитетного состояния |
| Доказательство | запись о проверке, привязанная к точному SHA и run id; доказательство само по себе не даёт полномочий |
| Принятие | переход, после которого изменение становится частью авторитетного состояния |

## 1. Что где хранится

| Данные | Этап 1 | Этап 2 |
|---|---|---|
| Код ядра, тесты, workflow | main (авторитетно) | main |
| Схема очереди, `QUEUE_VERSION`, миграции | main | main |
| Политики (`AGENTS.md`, лимиты, allowlist обработчиков) | main | main |
| Декларативные задачи (`TASKS.json`) | main | main |
| Изменяемая очередь (`TASK_QUEUE.json`: статусы, история, аренды) | **временная**, живёт один запуск; исходная очередь берётся из main или создаётся пустой | **ветка `state/queue`** (авторитетна только для очереди) |
| Записи проверок (PASS/FAIL, ревизия, run id) | внутри временной очереди и в артефакте как доказательство | в коммитах `state/queue` |
| Аренды | временные | в `state/queue`, переживают запуск только до `LEASE_TTL` |
| Логи, отчёты тестов, артефакты CI | временные; это доказательства, а не состояние | то же |
| Принятые изменения кода | только PR + слияние владельцем | то же |

Правило для обоих этапов: **артефакт Actions никогда не является авторитетным состоянием.** Его можно читать как доказательство конкретного запуска, но восстановить из него очередь нельзя.

## 2. Этап 1: временное состояние

**Что гарантируется:**
1. Запуск начинает с очереди из main (или пустой) на SHA, которым он запущен. SHA и run id пишутся в результат.
2. Один запуск работает с одной задачей (`run_cycle`). Аренды и `LEASE_TTL` защищают от двух исполнителей внутри запуска.
3. Конец запуска: очередь и доказательства выгружаются как артефакт-доказательство. Следующий запуск их **не читает**.
4. Изменение очереди становится постоянным только через PR в main и слияние владельцем.

**Что явно не заявляется:** автономное продолжение между запусками, накопление истории без человека, «непрерывный цикл».

**Восстановление после сбоя:** упавший запуск ничего не меняет в авторитетном состоянии. Повторный запуск начинает с того же main. Дубли исключены, потому что в main ничего не записано.

**Отключение:** `--disable-file` (уже есть) и переменная `AUTOPOIESIS_CYCLE_DISABLED` для workflow. Исход `DISABLED` (код 0) отличается от `RECOVERY_REQUIRED` (код 3).

**Последствия для существующего кода:**
- restore между запусками (`queue_snapshot.py` restore, `restore_fault_gates.py`, шаги restore в `ci.yml`, `scheduled_state.py`, #40/#46/#49) на этапе 1 не нужен;
- проверка целостности артефакта остаётся полезной как проверка доказательства;
- решение «удалить или сохранить как библиотеку доказательств» — отдельный вопрос для G4-ревью, а не часть этого черновика.

## 3. Этап 2: ветка операционного состояния

Включается только после отдельного решения владельца: нужна job с `contents: write` в одну ветку.

**Устройство:**
- ветка `state/queue` содержит только `TASK_QUEUE.json` и `STATE_MANIFEST.json`, без кода;
- писатель один: workflow цикла с `concurrency: group: state-queue, cancel-in-progress: false`; права на запись только у последней job, а исполнение обработчика идёт в другой job без прав (см. G3);
- запись только fast-forward. Новый коммит — потомок того, с которого запуск начал. Если ветку обновили за время запуска, push отклоняется, исход `RECOVERY_REQUIRED`;
- каждый коммит состояния несёт в сообщении: run id, SHA кода из main, `QUEUE_VERSION`, sha256 очереди.

**Проверки при чтении (fail-closed):**
1. ветка существует; если нет, то только явный bootstrap-ввод;
2. HEAD ветки — коммит, сделанный workflow цикла (автор и сообщение в ожидаемом формате; проверяемо, но не криптографически);
3. `QUEUE_VERSION` совпадает с кодом; иначе миграция отдельным шагом с резервной копией (как `migrate_queue_file`);
4. `load_queue` проходит;
5. SHA кода из манифеста — предок текущего main; иначе код откатили, исход `RECOVERY_REQUIRED`.

**Почему не артефакты.** У ветки неизменяемая история, происхождение через SHA, нет срока хранения, её видно глазами, а конкурентная запись решается fast-forward. Restore из артефактов на #63 занимает около 1800 строк кода и тестов. Чтение ветки — `git fetch` плюс `load_queue`.

**Какие ветки защищены:** `state/queue` получает свой ruleset: только fast-forward, без удаления. Ruleset `main` не меняется. Это настройки репозитория, решение владельца.

## 4. G3: гонка между проверкой и DONE

**Проблема.** Сейчас DONE пишется, если дайджест живого каталога `autopoesis/` равен протестированному. Каталог может измениться после последней проверки, но до записи (TOCTOU).

**Решение.** Принимается коммит, а не каталог.
1. Обработчик тестирует чистый checkout точного коммита. В CI это отдельная job `actions/checkout` с `ref: <sha>` и `permissions: contents: read`, без секретов. Локально — `git worktree add --detach <tmp> <sha>`.
2. Запись проверки содержит `commit_sha` и `tree_sha` (`git rev-parse <sha>^{tree}`), а не только дайджест каталога.
3. DONE привязан к паре (`commit_sha`, `tree_sha`). `revision_semantics = "tested_commit_tree"`.
4. Координатор проверяет, что `tree_sha` действительно дерево `commit_sha` (`git cat-file -p <commit>`). Объекты git неизменяемы, поэтому гонки больше нет.
5. Дайджест каталога остаётся дополнительной проверкой, но уже не гарантией.

**Тесты, которые должны быть (сначала красными):**
- изменение рабочего каталога после теста не влияет на DONE, потому что запись указывает на коммит;
- проверка с `tree_sha`, который не является деревом `commit_sha`, отклоняется;
- DONE с `commit_sha`, отличным от записанного в PASS, отклоняется при повторе истории;
- обработчик, который пишет в свой checkout, не меняет `tree_sha` коммита;
- миграция v2 → v3 сохраняет старые DONE с их меткой и не повышает их до `tested_commit_tree`.

Формат очереди меняется: это `QUEUE_VERSION = 3` и ещё одна миграция с теми же правилами, что v1 → v2.

## 5. Доказательства для перехода к автономности

| Утверждение | Минимальное доказательство |
|---|---|
| «Цикл работает» (этап 1) | run на main: COMPLETED на реальной задаче; артефакт-доказательство с SHA |
| «Цикл продолжается без человека» (этап 2) | два плановых запуска подряд на main; второй читает `state/queue`, записанную первым; оба run id и оба коммита состояния |
| «Восстановление работает» | запуск, убитый посреди выполнения (cancel), затем следующий: аренда снята по TTL, исход виден в истории |
| «Защита от гонки» | два одновременных dispatch: один fast-forward, второй `RECOVERY_REQUIRED` |
| «Выключатель работает» | запуск с выключателем: DISABLED, ветка состояния не изменилась (тот же SHA) |

Без этих run id автономность не заявляется.
