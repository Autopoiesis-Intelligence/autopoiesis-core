## RESULT

### 1. Риск `legacy_history_length` и сортировки

**Механизм.** `merge_candidates` сортирует всю историю по `at`. Если часы отстают от записанных событий, новое `CANDIDATE_ADDED` встаёт внутрь перенесённого префикса и сдвигает последнее legacy-событие за границу. Других записей, которые меняют порядок, нет: `advance_task`, `record_verification_file` и восстановление аренд только дописывают в конец.

**Почему это не может дать ложное принятие.** Повтор истории проверяет DONE по одному из двух правил:
- внутри границы — старая семантика и совпадение с ревизией PASS;
- за границей — только `tested_commit_tree` и совпадение commit/tree.

Сдвиг через границу переводит DONE под другое правило, и оно его не пропускает:
- старый DONE за границей отклоняется (тесты 7 и `reordering`);
- новый DONE внутри границы отклоняется (`a_commit_bound_done_inside`).

Значит, перестановка даёт только ложный отказ, не ложное принятие. Это fail-closed.

**Слабое место.** `update_queue_file` пишет результат слияния без повторной проверки. При сдвиге часов файл записывается в состоянии, которое следующий `load_queue` отклоняет. Работа останавливается до ручного восстановления из `.v2.bak` или истории. Тест фиксирует это поведение как есть.

**Предложение, отдельной задачей.** `merge_candidates` дописывает новые события в конец, не пересортировывая старые, и проверяет результат перед записью. Это меняет код очереди, поэтому в G3-R не входит.

**E4 — изоляция прав обработчика.**
- Цель: обработчик выполняется в отдельной job или процессе без секретов, без `GITHUB_TOKEN` с записью и без доступа на запись к очереди и рабочему каталогу. Результат передаётся координатору только как файл ограниченного размера.
